# slap5 web

The browser demo: a 15×15 gomoku page whose opponent is the engine in `../engine`, compiled to WebAssembly
by the adapter in `../crates/slap5-wasm`. It is the page that used to run a JavaScript engine, with the
search replaced; the UI, the game rules and the worker's message contract are the ones that page already
had.

## Commands

| Command | Purpose |
| --- | --- |
| `npm install` | Install Vite |
| `npm run dev` | Build the wasm package, then serve the page |
| `npm run build` | Build the wasm package and the production site into `dist/` |
| `npm run preview` | Serve the production build |
| `npm test` | Run the browser-side tests in Node |
| `npm run build:wasm` | Just the wasm build |
| `node scripts/measure-levels.mjs` | Run the wasm engine on suite positions and print the depth each level reaches |

The wasm build needs the `wasm32-unknown-unknown` target and a `wasm-bindgen` CLI matching the pin in
`crates/slap5-wasm/Cargo.toml` (`cargo install wasm-bindgen-cli --version 0.2.129 --locked`). It writes
`src/wasm/`, which is generated and not committed; `npm run dev` and `npm run build` run it for you.

## Module map

| Modules | Responsibility |
| --- | --- |
| `src/main.js`, `src/ui/view.js`, `src/style.css` | Page bootstrap, DOM rendering, styles |
| `src/game/controller.js`, `src/game/setup.js` | Game phases, board setup, the AI request lifecycle |
| `src/core/constants.js`, `src/core/bitboards.js`, `src/core/rules.js` | Dimensions, occupancy words, rules, legal fallback |
| `src/core/moves.js` | The move played before the engine has answered |
| `src/ai/client.js` | Worker lifecycle, request ids, the last completed search result, progress timing |
| `src/ai/worker-handler.js` | The worker's message contract; the engine is injected |
| `src/ai/wasm.js` | Loads the wasm module, packs positions, turns iterations into progress |
| `src/ai/difficulty.js` | The four levels, as (time, depth) budgets |
| `src/worker.js` | Worker entry: installs the handler with the wasm engine |
| `src/wasm/` | Generated by `scripts/build-wasm.mjs` |

`ai/worker-handler.js` deliberately does not import `ai/wasm.js`: the wasm module's asset import is a
bundler URL that plain Node cannot resolve, so the engine is chosen in `worker.js` and the handler stays
testable.

The progress bar has to fill gaps, because the engine reports once per completed iteration and those reports
get further apart as it deepens. The client keeps a 120 ms tick (`progressTickMs`) that advances the bar
with the higher of two estimates: elapsed time against the level's budget, and a saturating approach to the
*next* depth's share of the bar, paced by how long the last iterations took. It is monotone, it never claims
a depth the engine has not reached, and it stops at 95% until the search reports the move - so the bar cannot
be full while the engine is still thinking.

## Board geometry

The stones go on the *crossings* of a 15×15 lattice, not inside squares, and the DOM is a 15×15 grid of cells
whose centres are those crossings. `view.js` prepends one `<div class="lines">` under them, and the stylesheet
draws the lattice on it:

- `.lines` covers exactly the cells (`inset: var(--pad)`), so its width is 15 cells and crossing *i* is at
  `(i + 0.5)` cells.
- The lines come from tiling a **one-cell** background with the line at the tile's centre. A repeating
  gradient with the line at its period *start* would put the last line of each direction exactly on the box
  boundary, where nothing is painted - which is how the board lost its right and bottom edges.
- `.lines::before` carries the vertical lines and is inset half a cell top and bottom, `::after` the
  horizontal ones inset half a cell left and right, so every line runs from the first crossing to the last
  rather than into the margin. The four star points are backgrounds on `.lines` itself.

The cells are invisible (no border, no background) and are only click targets, one per crossing; hover
previews a stone as a soft disc. Anything that moves a stone has to keep it centred in its cell, which is what
puts it on the crossing.

## Deployment

`.github/workflows/pages.yml` runs `cargo test`, `npm test` and `npm run build`, then publishes `dist/` to
GitHub Pages. A project page is served from `/<repo>/`, so the workflow sets `VITE_BASE` (and
`vite.config.js` defaults to `'./'`, which also works for a user page or a custom domain).
