# Improvement queue

The order the evidence supports as of 16 October 2026.

The only change in this work that won games was **futility pruning**, which deletes subtrees. Every change that only shaved depth or bought speed was level on games: the two-dimensional reduction table (`lmr-table`, 25W-71L over 100 games against Tito), IIR (`iir`, 30W over 93 games), and the three local optimizations (deferred evaluation, the read-only bit iterator, the bulk discard of the pruned tail), which together bought 5-7% more search per second and changed no result. So deletion-class work first; speed-class work is expected to be neutral unless it buys a whole ply.

Where we stand, for calibration: roughly **1450-1550** in freestyle15 terms. The two usable near-equal opponents are **KANEC** (1478, 816 rated games, opposition averaging 1328) and **PELA 2023** (1549, 1320 games, opposition 1514). Use `external/pela/pbrain-pela.exe` for the latter: that is the build the rating refers to. Piskvork's bundled `external/piskvork/bin/pbrain-pela.exe` is a different, much smaller build of the same version string and must not be used for measurement. That switch was made on 16 October 2026 - `pbrain-pela_20261016_023711` is the first pool run with the right binary - so every pela pool before it used the bundled copy, and the pela figures quoted in this file and in `algorithm.md` (futility's per-block wins, the null-move block's pela line, the cap experiments' pela games) were measured against the wrong build and are not comparable with anything run from here on. Those numbers need re-measuring before they are used as reference points, and `run-info.txt` in each run directory names the binary, so which side of the switch a run falls on is checkable rather than remembered. Tito (1764) beats us and Rapfi (2716) sweeps us 20-0.

## Measurement rules

Unchanged from the earlier work.

- A mechanism lands behind its own switch, default off, with the default path untouched until a pool says otherwise.
- Equivalence gates: the 62 tests, the position suite (21/21) twice, and a fixed-depth or fixed-position comparison showing identical moves, scores, depths and `Stats` where the change is supposed to be an equivalence.
- Strength gate: 100-game pools (five 20-game blocks on held-out openings 25-34) against KANEC and pela, tallied per block, with truncated and error games counted separately.
- Twenty games cannot see a 20-Elo effect. The block-to-block swing of one binary is 3-9 wins out of 20, and the standard error of a 100-game difference is about six wins.
- No item is adopted on a Rapfi result. At 0-20 there is no resolution to gain there.

## 1. In-node VCF (deletion class)

A bounded forced-win search for continuous fours, run inside a node, returning a fail-high cutoff or nothing.

Why first: it attacks the loss mode we can reproduce. Against Rapfi we are mate-proved while at depth 1 with 112 nodes spent, where Rapfi reports depth 26 and finds its mate in 3 in 50 nodes; against Tito the recorded losses arrive in about twenty moves per side, which is forced play. Half the nodes in a probe position were `forced` nodes, so this is work we already do - the general search does it with a window, a table and move ordering, a dedicated bounded search does it with neither.

Cost and risk: a node budget per call, and wasted time in quiet positions. That risk is removable by construction: gate the call on a mask already computed at every node (the side to move has a four, or an open three) plus a depth cap, and the quiet-position cost is zero rather than small.

Work: the bounded fours-and-open-threes search, a per-turn node budget, the guard, a `Stats` counter, a switch. Verify with the suite, then a corpus of the Rapfi endings from `logs/pbrain-rapfi_avx2_20261016_020338/*.psq` as a deterministic does-it-now-prove-the-mate check, then the 100-game pools.

**Status, 16 October 2026: implemented and measured too expensive.** The proof is in behind `vcf` (default off) with `vcf=N` setting its node budget: `proof_node`/`four_answered` in `src/search.rs`, fours only, an exact mate distance (`MATE - plies - 1`, offset by the node's ply because `verify_mate` re-searches at that distance), and the guard that keeps it out of quiet positions. It reproduces the expected behaviour - the dose-response is monotone in the budget, which is what rules out a false-proof bug - but even the smallest budget costs a suite position and a ply of depth: default 21/21 at depths 5-8, `vcf=50` 20/21 at 4-6, `vcf=200` 19/21 at 3-7, `vcf=1000` 18/21 at 2-6. The cause is structural rather than a tuning problem: every proof node calls `Board::shapes()` to rebuild the masks, so a proof costs milliseconds where the subtree it might save costs microseconds. The next step is therefore to make the generator cheap before touching the budget - reuse the calling node's `Shapes` for the first move, and compute deeper four masks incrementally (per-cell line updates) instead of from scratch, or run the proof only at plies where a huge four set cannot occur. Until then the switch stays off and `Stats::vcf_nodes`/`vcf_proofs` will show how often the guard fires in real games.

**Measured 16 October 2026: not a performance gain either.** With the adaptive gating in place, a fixed-depth comparison (`vcf_saves_subtrees_or_only_costs_nodes`, depth 5, mate check off, so nothing depends on the clock) shows **zero** node savings and **zero** proofs found on four positions - a chain of fours, a double three and two quiet boards - while spending 2108 and 1648 proof nodes on the quiet ones. The mate positions gain nothing because they are already won by the existing forcing machinery (free four replies and `Threats::decided`), and the guard never even fires there: it excludes forced nodes, and in a four chain the winning nodes are forced. So VCF as gated searches exactly where the engine already wins without it, and pays nodes everywhere else. That is consistent with the earlier neutral results for `no-three-ext`, `free_four_replies` and the counter-threat reply: this engine's forcing play is already carried by the node rules rather than by a dedicated prover. The mechanism goes in the drawer unless a future version both widens the guard (so it can fire in the chains where proofs would matter) and makes the generator cheap (one class instead of a full `Shapes` per node) - and even then the burden is on a pool, not on the suite. The mechanism was then **removed from the source** (16 October 2026): the finding and the two measurements above remain, and the code is in the git history if a future version with a cheap generator and a wider guard wants to start from it.

## 2. Null-move pruning (deletion class)

**Implemented 16 October 2026; first measurement positive.** Behind `null-move`/`no-null-move` (default off), `null_reduction: 2`, `Stats::null_nodes`/`null_cutoffs`, and a `Searcher::nulls` counter that stops the search becoming a chain of free moves. Guards: `!root && !forced && nulls == 0 && depth >= 4 && opp_five.is_zero() && static_eval >= beta` - the pass must be legal in effect, and passing from a position that is not already good is how this mechanism misses the opponent's win. `null_move` joined the condition that decides whether the static score is computed, since the guard reads it. Fixed-depth ledger (depth 6, mate check off): **7.5% and 9.4% fewer nodes** on two quiet positions (67 and 153 passes, 4 and 90 cuts), **0.0%** on a chain of fours, a double three and a sharp midgame where the guards exclude it and no pass is tried. Unlike VCF it saves where it fires and costs nothing where it does not, and the saving is not only cuts - the null search fills the table with the opponent-to-move position, which is why a 6% cut rate still saved 7.5%. The suite reads 21/21 at depths 5-8 with it on. Remaining: the second suite run, then the 100-game pools against KANEC and pela as an arm binary, expecting modest strength movement (the three local optimizations bought 5-7% of time and changed no result) but with the class in its favour - subtree deletion, like futility.

**Adopted as the default, 16 October 2026**, on the rule that a mechanism which is not measurably harmful and saves nodes at every time control is worth keeping: `null_move: true` in `Config::default`, with `no-null-move` as the escape hatch. The suite read 21/21 twice with it on, the fixed-depth ledger is positive, and the KANEC pool finished at **48W-47L-5E over 100 games** (48% with the five voids counted separately, 50.5% of decided games), with per-block wins of 14, 8, 10, 7 and 9 - a seven-to-fourteen win swing per block from the same binary, which is why the rule here is 100 games and not 20. The default binary's own record on these openings is 11W-9L (55%) and 9W-10L-1E (45%), so the pool is level: the mechanism is kept **on cost, not on strength** - the fixed-depth ledger is positive, the suite is unchanged at 21/21, and the games show no harm and no gain. Note the baseline is thin: a 100-game pool with the default binary would be the like-for-like control, and without it "48% versus 55%" is one noisy block against another. The correction to the intuition that it matters more at longer controls: a speed saving is worth roughly the same Elo at every control (both the clock and a speedup move the engine along the same depth-versus-strength curve), so the argument for a default is that the saving is real at *all* controls, not that it grows.

Two things to revisit. First, the guard leans on `static_eval >= beta`, and this evaluation has no tempo or initiative term - exactly what a free opponent stone buys - so the mechanism's failure mode is a false cut in a position where the free move creates a threat the evaluation underrates. Adding the tempo term (item 3) makes the guard more trustworthy, and `Stats::null_cutoffs` stays visible to see how often it fires in real games. Second, the shipped binary's hash (`14B4C6585786C9A0`) did not match the arm's (`F96DD36E92C2F6E6`) even though the two were built from the same source state under incremental compilation, so hash equality is not a reliable identity check here - the source state, or a clean rebuild, is.

Rapfi has it (`nullMoveReduction`, with a per-rule bias); we have none. It deletes subtrees at quiet nodes: pass the move, search shallower, cut if the opponent still cannot profit. In gomoku the guard is what makes it safe - the opponent must have no four or five threat, and the position must not be a forced chain, or the pass is illegal in effect. Those masks already exist here (`opp_five`, `opp_open4`).

Why second: it is the same class as futility, which is the only thing that has worked, and it fires where futility does.

Cost and risk: a switch, a reduction constant and a guard set. The failure mode, if a guard is wrong, is missing the opponent's win - which the suite and the tactical corpus are built to catch.

## 3. Evaluation tuning

Our evaluation is twelve hand-set weights over per-direction shape classes (class values 3000/1500/300/100/25/8, plus two weight rows for ordering), with no positional term, no centrality, no tempo term, and own/opponent weights separated by hand. It has never been fitted to anything. This is the cheapest strength in the tree: no new code path, no new data structure, no new switch beyond a way to load alternative weights.

Three steps, increasing in cost: **(a)** fit the existing twelve numbers against a fixed opponent (KANEC) by hill-climbing or SPSA; **(b)** add the missing terms - centrality, tempo, and the blocked-three/two weights that currently do double duty as the development signal; **(c)** consider richer features only after that.

Why not later: it is also the prerequisite for any learned evaluation. A net trained on labels from a fifteen-hundred engine with untuned features would mostly learn to reproduce twelve numbers.

**Status, 16 October 2026: instruments built, no feature tuned yet.** Two clock-free, deterministic probes exist. `examples/eval_probe.rs` runs the 21 suite positions (seconds) and `examples/eval_from_games.rs` replays the `.psq` match records under `logs/` (about 90 s for 150 positions, sampling every `stride` plies past the opening, skipping positions where either side can complete five). Both report the agreement between the static score at the root and a fixed-depth search, with mate scores excluded and counted separately, because a count model has no vocabulary for "mated in n" and including them reads as r = 0.10 where the real figure is r = 0.72.

The readings so far, and they are consistent in shape rather than in sign:

| corpus | n | r | sd(residual) | mean | decided |
|---|---|---|---|---|---|
| suite positions | 15 | 0.724 | 456 | -186 | 6 of 21 |
| game records | 80 | 0.552 | 1062 | +878 | 70 of 150 |

Residuals grow with the phase (mean 643, 839, 1151, 1081 across the four stone-count bands), which is the first evidence-backed candidate feature: the static model misses more as threats accumulate, so a phase scaling or an unblockable-pattern count is the thing to try, not a global reweighting. The sign of the bias differs between the two corpora (the suite is all lost positions, the game sample is not), which is a reason to keep both and split by phase rather than pool them.

Three things to know before tuning anything. First, **the labels are circular**: both probes label with our own fixed-depth search, so a feature that lowers the residual can be fitting our own blind spots; the fix is a subsample labelled by Rapfi, which prints its own evaluation in its run logs (`Eval +M3` and numeric forms) and is far stronger than us. Second, **half the sampled game positions are decided at depth 6** (70 of 150), so the corpus wants sampling deeper into quiet lines rather than more games. Third, the **`.psq` record format**: the first line is a header (`Piskvorky 15x15, 4:4, 0`), the move lines are `x,y,time-in-milliseconds` - the third field is *not* the player, the first few lines are Piskvork's opening stones, and the players alternate from the first recorded stone, whose identity the run directory name (`_high5_first` / `_opponent_first`) fixes. Reading the third field as the player silently produces single-colour boards, which are forced wins, which is why the first version of the instrument reported 150 of 150 positions as mates.

Next: grow and split the corpus (more records, deeper stride, a Rapfi-labelled subsample), then fit `VALUE`'s twelve numbers on the fit split against the agreement objective - not against game results, which at 100 games carry the seven-to-fourteen win block swing measured on the null-move pool. Any candidate that lowers the residual must still pass the suite (21/21), the node-rate budget (the eval must not cost more than about 5% of the node rate, measured against a constant-eval scratch build), and then a 100-game pool against KANEC before it is believed, with pela as the second rung. And no scale change without re-checking the pruning coupling: the futility (`150 + 120*depth`) and razor (`200 + 150*depth`) margins are in eval units, and null-move's guard reads `static_eval >= beta`.

**Practical note on corpus size, learned the hard way:** the labelling search is single-threaded and fixed-depth, and a 300-position run at depth 6 (`eval_from_games 6 300 6`) did not finish in fourteen minutes, so it was killed. Depth 6 on late-game positions runs straight into the forced-chain explosion that dominates our tree, which is also why half the samples come back decided. The usable configuration is the 150-position, stride-4 run that completes in about ninety seconds, and growing the corpus needs parallelism over positions (the obvious fix, with unchanged semantics since each position is independent) or a lower labelling depth for the bulk with a small deeper subset kept for validation - not a longer wait.

**Corpus, second pass, same day: the instrument was the bottleneck, and it is fixed.** The labelling loop was doing two expensive things it had no reason to do: allocating a fresh 32 MB transposition table per position instead of one per thread, and splitting work into equal-*count* chunks when a late position costs ten to fifty times an early one, which left fifteen of this machine's sixteen logical processors idle behind a straggler (an 842 s-CPU run at 330 s wall is what that looks like). One searcher per thread plus a shared work cursor, and labelling 400 positions at depth 5 takes **22 seconds**. The same 400 at depth 6 was still on its last stragglers after nine minutes and was stopped, as was a 2000-position pass at depth 5 after eight minutes - the tail is the late-game forced-chain explosion, and it dominates any single pass however large. Grow the corpus in 400-position passes at different strides, or cap per-position nodes for the bulk, rather than asking one pass to swallow the tail.

The reading from that pass, on 277 usable positions of 400 sampled (stride 6, depth 5): **r = 0.653, sd(residual) = 942, mean = +751, 123 decided.**

| stones | n | mean residual |
|---|---|---|
| <10 | 86 | 666 |
| 10-19 | 101 | 791 |
| 20-29 | 31 | 877 |
| 30+ | 59 | 740 |

**This weakens the phase-scaling case I made from the first pass.** The stride-4, depth-6 run showed a clean gradient (643, 839, 1151, 1081); the larger and better-sampled pass is nearly flat (666, 791, 877, 740), so the gradient was mostly the earlier sample's shape - heavy on early positions, high decided share - not a property of the evaluation. Do not add a phase multiplier on the strength of the first reading.

What the outliers *do* support is narrower and more concrete. The five worst residuals are all the same failure: `static -2753` against `search -513`, `-2245` against `-191`, `-992` against `+993`, `-1280` against `+628`, `-1862` against `-68`. Every one is a lost or losing position where the static score is one to two thousand points too pessimistic, and the magnitudes are in the same direction as the suite probe's mean of -186. That points at the defensive branch of the evaluation - how much the opponent's accumulated threats should cost us when we are already behind - rather than at any global or phase-scaling term.

What the corpus now supports, for item 3: a fit/hold-out split of roughly 200/77 over the stride-6 depth-5 sample, enough to fit one or two parameters against the agreement objective and check them on positions the fit never saw. It does not support fitting twelve numbers, and every label in it is still our own search's opinion.

**Corpus, third pass: four strides, ~1,000 usable positions, and the phase question settled by noise.** Running the same 400-position sample at strides 4, 5, 6 and 7 (22 s each) gives four largely disjoint position sets:

| stride | usable | decided | r | sd(residual) | mean |
|---|---|---|---|---|---|
| 4 | 250 | 150 | 0.673 | 958 | +764 |
| 5 | 241 | 159 | 0.745 | 813 | +591 |
| 6 | 277 | 123 | 0.653 | 942 | +751 |
| 7 | 273 | 127 | 0.719 | 730 | +506 |

About 1,040 positions in ninety seconds of compute, which is enough for a 700/300 fit and hold-out split. The aggregate reading is r about 0.70, sd about 880 - roughly one four's worth against a score range of thousands, and about one shape class apart.

Two conclusions worth having before any parameter is fitted. **First, the phase band means are not stable across strides** - stride 4 reads 752, 749, 832, 730 down the bands, stride 7 reads 325, 900, 466, 415 - so the spread between bands is no larger than the spread between samples of the same bands. Phase is not resolvable at n of 250 to 280 per pass, and a phase parameter fitted on one pass would be fitting that pass. The honest position is that phase scaling is unsupported, not merely weaker than it first looked.

**Second, the mean residual is the least actionable number in the table.** Our score enters the search only through differences - futility margins, razor margins, and the null-move guard all compare one static eval against another - so a uniform offset cancels everywhere and would change nothing about which move is chosen. The mean of +506 to +764 says the static model reads positions about six hundred points lower than a depth-5 search does, and that is consistent with a count model that under-weights forcing continuations; but no parameter should be fitted to it. What is actionable is the *structure*: sd ~880 with a fat tail of positions where static is one to two thousand too pessimistic, and the fact that this structure persists across strides and depths means the per-position residual is a property of the positions, not of the sample. That is the dependent variable to model, with the features it correlates with as the independent ones - which is what item 3 step (b) should actually consist of, rather than a search for twelve better constants.

**Sizing the disagreement (stride 6, depth 5, n=276):** |residual| p50 571, p90 1606, p99 1857; 31% over 1000, 17% over 1500, and only 2 of 276 over 2000. So the disagreement between the static model and a depth-5 search is *bounded* - about half a shape class for the median position and under one and a half fours at the 99th percentile - which is the headroom answer for the whole item: nothing in the evaluation is wildly wrong, and no single feature can win more than a few hundred points of accuracy across most of the corpus.

Where it is wrong is specific and consistent: the tail (|residual| > 1500, n=47) is **100% static-negative, mean static -1773, mean 14 stones** against a bulk of mean static -523 and 21 stones. So every bad residual is a position the static model reads as thoroughly lost (below -1500) and the search refuses to confirm, and the tail sits in the *opening*, not the endgame. That is a one-parameter claim with a measurable form - the eval's negative branch is over-scaled, and positions below about -1500 should be read some 1500 less pessimistic - and unlike phase scaling it does not depend on band means that move with the sample.

**The confound to settle before fitting it:** a depth-5 search that has not proven a loss returns a mild score, so this tail could equally be *unproven* losses rather than over-pessimistic evaluation, and the decided filter only removes proven mates. The test is cheap because the tail is early-game and therefore cheap to search: relabel those positions at depth 8 and see whether the search moves toward the static verdict. If it proves the losses, the tail is decidedness leaking through the depth-5 label and no eval parameter should be fitted to it; if the gap survives, the parameter is real. That test comes before any fit, for the same reason the futility and null-move work was gated: a parameter fitted to a measurement artefact is worse than no parameter.

**The test is blocked by the sampler, not by the search, and here is the fix to write before trying it again.** Depth-8 labelling at 30 sampled positions takes 77 s and yields 13 usable (decided share rises to 57% at depth 8 against 31% at depth 5, with no residual over 2000 surviving - directionally, part of the tail is shallow-label decidedness). The same at 60 sampled positions was still on stragglers after eight and a half minutes and had to be stopped, because position cost grows with both depth and position age while the sampler walks the corpus in file order with no cost control. Two ways out, both small: cap nodes per position (deterministic, with the capped count reported) or add a filter that selects only the positions under test - the tail is defined as static below -1500, and there are about 47 of those in a 400 sample, nearly all early-game and cheap, so a `--min-pessimism` flag turns the confound test from an eight-minute straggler run into a few seconds of work. Until one of those exists, the honest statement is that the tail's cause is unknown: part is shallow-label decidedness, part may be over-pessimistic evaluation, and the split between them is unmeasured.

**The `--min-pessimism` filter exists now (fifth argument), and running it exposed the real limit on corpus coverage.** `eval_from_games <stride> <max> <depth> [dir] [min_pessimism]` keeps only positions whose static score is at most `-min_pessimism`, so the tail can be relabelled at a depth the whole corpus could never afford. It works, but two things make tail-only labelling slower than the unfiltered passes rather than faster: deeply pessimistic positions are the tactically loaded ones (large trees at any depth), and the filter forces the sampler to replay the whole record set instead of filling its quota from the first files. That last point is the discovery - there are **1,699 `.psq` records** under `logs/`, and the quota-based sampler means the entire four-stride corpus above, all ~1,040 positions, was drawn from the handful of runs that sort first. Every number in this file with "corpus" in it describes a few games, not the corpus, and the fix is a per-file quota (one or two positions per record, spread over all 1,699) rather than a global quota. That should be the first change next session: it multiplies the available positions by the number of games and costs nothing but the walk.

**Done, and it changes the headline: on a diverse corpus r = 0.478, not 0.70.** One position per record (stride 4, depth 5, max 1000) gives **987 usable positions from hundreds of games, only 13 decided (1.3%)**, against 0.65-0.75 and 31% on the few-game samples. So the earlier agreement figures were measuring how alike the first few games are, and the honest baseline for item 3 is r ≈ 0.48 with sd 915. The decided-share problem was largely an artefact too: sampling one early position per game instead of late positions from a handful of games takes it from 31% to 1.3%.

The tail, however, survives in exactly the same shape on the diverse corpus: 176 of 987 positions (18%) have |residual| > 1500, **100% of them static-negative, mean static -1691, mean 8 stones**, against a bulk of mean static -375. Median |residual| is better (391 against 571) and the extremes are worse (20 positions over 2000 against 2, the worst at 2475). A phenomenon that holds on 47 positions from a few games and on 176 from hundreds of games is not an artefact of sampling, so the "static reads a position as thoroughly lost and the search refuses to confirm" signature is the real feature target. The unresolved confound from the depth-8 test still applies to its *cause*, not to its existence.

Two sampling faults to fix in the same breath. First, **duplicates**: the same position appears in several records (the worst residual list shows `p00_opponent_first#8` three times with search values 1212, 1157 and 975 - one position, one board, three different depth-5 verdicts), because the same opening is replayed across pools; the corpus needs deduplication by position before any fit, or repeated games will dominate it. Second, **phase coverage collapses** under a one-per-file quota: with the offset fixed at the first qualifying ply, 982 of 987 positions are under ten stones, so the quota needs a per-file ply offset (file *k* sampled at ply *k* mod something) to spread the sample across the game rather than across the opening.

**And one consequence of the speed fix that must be settled before any fit: labels are now order-dependent.** Reusing one searcher per thread means the transposition table carries over between positions, which is why one board (`p00_opponent_first#8`) scored 1212, 1157 and 975 at the same depth in three different records: the score depends on what the thread searched before. The allocation I removed to save 32 MB per position was also what made each label reproducible. Either clear the table between positions (if `Searcher` exposes that) or keep the reuse and report the jitter as part of the label's noise - but a fit must not chase structure finer than that jitter, and no corpus number is reproducible across thread counts until this is decided.

**Phase-diverse sampling, and the rule that every number carries its depth *and* its phase mix.** Adding a per-file ply offset (file *k* sampled near ply 8 + 8*(k mod 24)) fills the bands - 69 / 43 / 43 / 47 across <10, 10-19, 20-29 and 30+ stones, where without it the corpus was 982 / 5 / 0 / 0 - and the reading moves to r = 0.597, sd 852, with 202 usable of 600 files and 115 decided (36%). So the same evaluation reads r = 0.433, 0.470 or 0.597 depending only on the sampling shape: all-opening samples sit near 0.45, phase-diverse samples near 0.60. Three configurations, three answers, one evaluation - every r in this file must be quoted with its depth and phase mix or it means nothing. The tail survived again (25 of 202, 12%, 100% static-negative, mean static -1714), its worst members now in the mid-game (`#16`, `#32`) rather than the opening, which is what a property of positions rather than of a ply looks like. That is five samples, five sampling shapes, the same tail signature, and band means still non-monotone (543, 862, 428, 675) for the third time.

**The evaluation's accounting was wrong, and that is fixed.** `shape_score` summed the bits of the per-class shape masks, and those masks hold the cells where playing *creates* a shape - so one open three set two or three neighbouring bits along its direction, every perpendicular direction added its own, and a single threat was charged two to four times. It now counts groups of adjacent cells, which is threats. The eval's numbers therefore shrank: measured with `scripts/retune.ps1`, the ordinary-position mean came to 0.691 of the shipped revision's. That matters beyond tidiness, because the futility margin, the null-move condition and the horizon return all compare those numbers with values the search computed, and `150 + 120·depth` is justified only by game blocks measured in the old units. The class values are therefore scaled 1.2x, to `[3600, 1800, 360, 120, 30, 10]`, which restores the average magnitude without touching the classes' relative weights.

The factor is a bracket, not a measurement. Node count at equal depth against the shipped revision read 0.936 at 1.0x, 1.070 at 1.45x and **0.974 at 1.2x**; the trigger rate that the margin actually controls, `pruned` per node, read 2.218 against the shipped 2.281 at 1.2x. KANEC over 100 games at 1 s per move: **53W-46L-1E** against the shipped build's 48W-47L-5E, blocks 60/55/35/55/63 - level to slightly ahead, not established, and the run tests the counting fix and the scale together. 64 tests pass, no truncations, one unexplained engine error.

Three things are open on this. The scale wants a fixed-depth measurement of the trigger rate - nodes and `pruned` per position with the clock out, which is deterministic - instead of node ratios and a factor that happens to end in a zero. `Stats::null_nodes` is unmeasured, and the null-move condition has no margin, so it fires less often now that the evals are smaller. And the error game needs looking at: one in a hundred can be a Piskvork hiccup or our side misbehaving.

**The first change the corpus chose, and it won games.** The feature correlations said the eval overpriced its own fours and underpriced its own open threes: with the residual being search minus static, `fours` (ours minus theirs) correlated **-0.672** and `open threes` **+0.574** over 90 positions. The four-to-open-three ratio was therefore moved from 3:1 to **1:1**, and the whole set scaled 0.9 so the average magnitude stayed where the margin was tuned - `VALUE = [3240, 1620, 162, 162, 27, 9]`. Every error term shrank in the predicted direction: r(fours) -0.672 to -0.565, r(open threes) +0.574 to +0.455, sd(residual) 1147 to 1023, median 500 to 480, residuals over 2000 from 14 to 4, tail mean static -1791 to -1635. KANEC, 100 games at 1 s per move: **57W-41L-2D = 57%**, blocks 55/70/40/65/58, against 53W-46L-1E for the counting fix at 3:1 and 48W-47L-5E for the shipped revision. The two draws are KANEC's stalled long games, killed by hand; `match.ps1` reports both those and a genuine engine failure as `E`, which is why the tally needs reading against the run directory.

Two qualifiers stay attached to that number. The block spread (40 to 70) makes it suggestive rather than proven at 100 games, and the correlations it was chosen from were measured against our own search, so part of the agreement may be fitting the judge rather than the game. Also, the same change raised node counts in forcing positions by 12 to 35% - the eval prices an open three higher, so the search pursues more lines - which means fewer nominal plies at a fixed time in exactly the positions the suite covers. That did not cost the pool, but it is a real coupling and it is why the ratio wants re-measuring against quiet positions rather than the tactical suite.

**A tempo term, and it won games.** The colour split showed the eval pricing the two sides differently: with the sampler's parity grid fixed so both colours appear, 541 positions gave a mean residual (search minus static) of **+578 with black to move against +487 with white**, spreads identical (sd 571 and 564), and a smaller sample agreed in direction. A constant per side closes that gap - `TEMPO = 45`, added for black and subtracted for white - and unlike a global offset it does not cancel, because it shifts every line's value by a constant that depends on whose turn it is. One test had to change with it: `empty_board_scores_zero` became `empty_board_scores_only_tempo`, since an empty board now reads +45 for black, and that is the intent rather than an accident. Against KANEC over 100 games at 1 s per move: **59W-40L, 1 killed (KANEC's stalled game) = 60% of decided games**, blocks 65/58/40/70/65, against 57W-41L-2D for the same build without the term - and four of five blocks at or above 58% where earlier builds managed two or three. Two caveats: the corpus is structurally blind to this term (it shifts static and the search's leaves alike, so the residual barely moves and could not be used to tune it), and the 45 is my half of a measured gap rather than a fitted number, so the size of the term is untested - the sign and the existence of the effect are what the runs support.

**The pela baseline is the tempo build, `CBC1374AE5FDB67E`.** Future evaluation changes are compared against it rather than against the shipped revision, because every pela figure recorded before 16 October 2026 came from the bundled copy of the engine and is not comparable with anything run now (see the calibration note at the top of this file). Baseline definition, so later runs match it exactly: `external/pela/pbrain-pela.exe` (sha16 `B97DF7A37C850D9C`, pela 7.9), engine `CBC1374AE5FDB67E` (counting fix, 1:1 four-to-open-three, 0.9 scale, tempo +-45) as the current baseline against `2CE48E0F5806323B` as the pre-tempo build - 100 games (50 pairs, each opening played both ways), 1000 ms per turn, 600 s match clock, Piskvork's default opening list, run directory `logs/pbrain-pela_20261016_*`. Read on points and per 20-game block, with ties reported: pela's games run long, so this pool is expected to truncate on the match clock rather than finish, and its record is **29W-56L-15D - 29% wins and 36.5% of points - against 28W-62L-9D, 1 killed, at 32.5% of points for the pre-tempo build (engine `2CE48E0F5806323B`), whose blocks were 35/44/28/29/20**. Truncations count as ties, not as missing games: pela's games run long, so a pool here is expected to tie on the match clock rather than finish, and the score to compare is points. The colour split is the sharper result - **19W-22L-9D as first mover (47% of points) against 10W-34L-6D as second (26%)** - which is the tempo effect in plain form, near parity as the first player against a 1549-rated engine and ground down as the second. Note that 50 pairs over a 41-opening list wraps: pairs 41-49 replay openings 0-8, so those repeats belong to the last block and a future run should either keep 50 pairs to match or cut to 41 pairs for a clean one-pass list.

**The sampler cannot yet buy size and phase together, and the fix is one run away.** One position per record means a deep position excludes short games: 202 usable from 600 files, decided share up to 36%. The per-file quota already takes consecutive qualifying plies, so raising `max` above the record count (per_file > 1, e.g. `eval_from_games 4 5000 5`) yields several positions per record at spread plies - size and phase at once - and that run is the first thing to do next session, followed by deduplication by position, since `p00_opponent_first#8` still occupies three rows of the worst-residual list.

## 4. Ordering and candidates

Two concrete defects, both measured in the earlier audit and both untouched:

- **The searcher never sees the real preceding moves of the game.** Recent-move proximity uses only the hypothetical search path, so at the root it does not know what the opponent actually just played. The protocol already hands us those moves; nothing consumes them.
- **The candidate radius is a fixed 2 cells** from any stone. PentaZen widens its range near the root while fewer than five stones are on the board, so our opening play starts narrower than theirs.

Why here: ordering and candidate changes are the cheapest way to turn a search that reaches depth 5-8 into one that reaches deeper on the same budget, and both defects are in the part of the engine the references differ from most. They change which moves exist or in what order they are tried, so they need the full gates - identical fixed-depth results where they are meant to be neutral, and a pool where they are not.

## 5. Transposition-table policy

One slot per hash, no replacement policy, no clustering. A deeper entry is never replaced by a shallower one - which the earlier audit measured as a cost, since a same-age entry belonging to another position is kept whole. Both references cluster their tables.

A clustered bucket - several entries, replace the shallowest or the oldest - is contained and testable (identical fixed-depth results under a table-on/table-off comparison harness). Expected effect is modest and mostly in node rate, so treat it as speed: adopt only if it buys enough to show up as depth.

## 6. Time management

The deadline is the full move budget (`self.deadline = start + limits.time`); there is no half-budget reservation in the current code, and the older claim that there was one was written against an earlier revision. What is still open is small but free: does the root loop start an iteration it cannot finish, and is the budget spent evenly across a game? Answer it with per-move elapsed times and `Stats`, not with a rating test. Anything more elaborate - extending on score drop or move instability - is a match question, and at 1 s per move it is likely to be noise.

## Rejected or deferred

- **The per-node double-threat mask**: measured at -4.5% in its own audit and +5.0% when re-measured on the current tree. A sign flip between runs is not a basis for a change.
- **Compact `Shapes`**: the memory saving is real and confirmed by the layout check (3072 -> 1920 bytes), the time delta is +2.7%, i.e. slower. Memory only, and this engine is not memory-bound.
- **Narrowing `Scores::shape` to `i16`**: the bound is 1800, so it fits, but it was never benchmarked.
- **NNUE or any learned evaluation**: deferred as its own project, deliberately not in this document. It needs a data pipeline (self-play at fixed depth, a few million positions), a trainer, an exporter, quantised inference, and an incremental accumulator hooked into `make`/`unmake` - and before any of that, a test that the incremental accumulator equals a full recompute at every ply, which is the classic silent failure of that design. It also needs what items 3 and 4 produce: a tuned classical evaluation as the baseline, and labels from an engine as strong as we can currently make it.
